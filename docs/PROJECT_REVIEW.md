# 프로젝트 회고

> 기술 용어를 많이 사용하기보다, 무엇을 맡았고 어떤 고민을 했는지 쉽게 설명한 문서입니다.

## 한눈에 보기

`마음의 날씨`는 감정을 글로만 저장하지 않고 날씨와 오브젝트로 보여 주는 서비스입니다. 여러 사용자가 광장에 감정을 남기면, 기록을 모아 AI가 한 장의 완성 이미지를 만들고 참여자의 편지함으로 보내 줍니다.

저는 4인 팀에서 **Java 백엔드 개발과 AWS 배포**를 맡았습니다. 특히 광장 기록을 저장하고, 완성 조건을 확인하고, AI 결과 이미지를 보관해 참여자에게 전달하는 서버 흐름을 구현했습니다. GitHub Actions, YAML과 환경변수 구성도 제가 담당했습니다. 백엔드는 Elastic Beanstalk에, 프론트엔드는 AWS Amplify에 배포했습니다.

## 사용자의 기록이 결과 이미지가 되기까지

1. 사용자가 광장에 감정과 오브젝트를 등록합니다.
2. 서버는 먼저 사용자의 기록을 데이터베이스에 안전하게 저장합니다.
3. 광장에 필요한 수만큼 기록이 모였는지 확인합니다.
4. 조건이 맞으면 참여 기록을 모아 AI에 이미지 생성을 요청합니다.
5. 완성된 이미지는 AWS S3에 보관합니다.
6. 참여자는 편지함에서 완성 결과를 확인할 수 있습니다.

저는 이 흐름이 처음부터 끝까지 이어지도록 백엔드 기능과 배포 설정을 연결하고, 프론트엔드도 AWS Amplify를 통해 배포했습니다.

## 기억에 남는 문제와 해결

### AI 결과를 기다리는 동안 요청이 길어질 수 있었습니다

AI 이미지 생성은 일반적인 데이터 저장보다 오래 걸리고 실패할 가능성도 있습니다. 두 작업을 한 번에 처리하면 사용자는 이미지가 만들어질 때까지 계속 기다려야 합니다.

그래서 사용자의 기록을 먼저 저장한 뒤, 이미지 생성은 별도 작업으로 이어지도록 분리했습니다. 덕분에 꼭 성공해야 하는 기록 저장과 시간이 오래 걸릴 수 있는 AI 작업을 따로 다룰 수 있었습니다.

개별 OpenAI 요청에는 일시적인 오류를 다시 시도하는 처리가 있습니다. 다만 완료 작업 자체를 오래 보관하는 대기열과 서버 재시작 이후의 자동 복구는 없습니다. 서버가 중간에 종료되거나 외부 서비스가 계속 실패할 때 작업을 이어가는 기능은 앞으로 보완해야 합니다.

### 서버를 다시 배포해도 이미지는 남아야 했습니다

운영 서버 안에 이미지를 저장하면 서버가 교체되거나 다시 배포될 때 파일이 사라질 수 있습니다. 그래서 AI가 만든 이미지는 서버가 아니라 AWS S3에 저장하고, 편지함에는 이미지 주소를 연결했습니다.

현재는 공개 기준 주소를 사용하는 방식입니다. 감정 기록이라는 서비스 특성을 생각하면, 다시 만든다면 비공개 저장소와 일정 시간만 사용할 수 있는 링크를 검토하겠습니다.

### 로컬에서는 되는데 배포 환경에서는 달랐습니다

내 컴퓨터에서 실행되는 것만으로는 배포가 끝난 것이 아니었습니다. 실행 파일의 위치, 서버 포트, 데이터베이스 연결, AWS 권한과 환경변수가 모두 맞아야 했습니다.

실행 파일과 설정을 배포용 ZIP으로 묶고, 서버 포트를 맞추고, 중요한 값은 코드 밖의 환경변수로 분리했습니다. 서버가 켜져 있는지 확인할 수 있도록 간단한 상태 확인 주소도 추가했습니다.

백엔드는 Elastic Beanstalk, 프론트엔드는 AWS Amplify로 나누어 배포했습니다. Amplify는 AWS 콘솔에서 설정할 수 있어 별도 YAML이 꼭 필요하지 않습니다. 전체 Git 이력에는 Amplify 설정 파일이 없으므로 실제 사용한 배포 서비스와 제 담당 범위만 적었습니다. 프로젝트가 끝난 뒤에는 유지 비용을 줄이기 위해 AWS 배포 리소스를 정리했습니다.

직접 추가한 `/`와 `/health`는 서버가 응답하는지 확인합니다. 별도로 Actuator의 `/actuator/health`에서는 자동 등록된 데이터베이스·메일 등의 상태를 확인할 수 있습니다. 현재 실행 안내는 이 경로를 우선 사용하며, S3·OpenAI와 실제 기능이 정상인지까지 확인하는 검사는 앞으로 보완해야 합니다.

### 저장이 끝난 뒤에 완성 조건을 확인해야 했습니다

새 기록이 아직 저장되기 전에 광장 완성 여부를 확인하면 마지막 참여 기록을 보지 못할 수 있습니다. 그래서 데이터 저장이 끝난 뒤 완료 확인이 시작되도록 순서를 정했습니다.

이 경험을 통해 비동기 작업에서는 “무엇을 먼저 끝내야 하는가”를 코드로 분명하게 보장해야 한다는 점을 배웠습니다.

## 팀 프로젝트에서 배운 점

- 내가 만든 기능도 다른 팀원의 통합과 개선을 거쳐 더 나아질 수 있다는 점
- 각자 만든 기능을 연결할 때 코드뿐 아니라 데이터와 실행 순서도 함께 맞춰야 한다는 점
- 배포 오류는 한 사람의 코드 문제가 아니라 설정, 권한과 실행 환경을 함께 확인해야 한다는 점
- 발표에서는 어려운 기술 이름보다 사용자가 어떤 경험을 하게 되는지 설명하는 것이 중요하다는 점

이 저장소에서도 팀 전체 기능과 제 직접 기여를 구분했습니다. 팀원이 이어서 개선한 내용을 제가 혼자 완성한 것처럼 적지 않았습니다.

## 다시 만든다면 보완할 점

1. 광장 완성과 이미지 전달 흐름을 자동 테스트로 확인하겠습니다.
2. AI나 S3 작업이 실패했을 때 다시 시도할 수 있는 구조를 만들겠습니다.
3. 감정 이미지가 공개 주소로 노출되지 않도록 접근 범위를 줄이겠습니다.
4. 서버뿐 아니라 데이터베이스와 외부 서비스 상태도 따로 확인하겠습니다.
5. 처리 시간과 성공·실패 횟수를 측정해 실제 수치로 개선 여부를 판단하겠습니다.

아직 측정하지 않은 성능 수치나 테스트 결과는 이 문서에 적지 않았습니다.
